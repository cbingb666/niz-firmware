# NIZ 66EC 主机通信与更新协议

协议由固件的 `host_command_dispatch` 和 HWI DLL 双向核对。离线实现位于 [niz_protocol.py](../scripts/niz_protocol.py)，只构造和解析字节，不连接设备。

## HID 报告布局

HWI 使用 Windows `WriteFile` 发送 65 字节：第零字节为 Report ID 0，后面是 64 字节载荷。载荷第零字节通常为 0，第一字节为命令，其后是参数或数据。默认描述符中的双向 64 字节通道位于接口 1，OUT 端点 0x01，IN 端点 0x82。描述符的接口字符串名称不作为协议判据；具体字节见 [metadata.json](firmware/tables/metadata.json)。

读取函数在收取 65 字节后去掉 Report ID，交给上层 64 字节载荷。下面的偏移都相对于这 64 字节载荷。

| 偏移 | 字段 |
| --- | --- |
| 0 | 前缀，通常 0 |
| 1 | 命令 |
| 2 至 63 | 命令数据或补零 |

## 已识别命令

| 命令 | 作用 | 证据入口 |
| --- | --- | --- |
| 0x3A | 加密固件记录 | 固件 0x918C，DLL 0x100039B0 和 0x10003B70 |
| 0xD0 | 恢复默认配置并重启 | 固件 0x77AC 调用 0x6144 |
| 0xD9 | 设置扫描使能值 | 固件 0x77AC |
| 0xE0 | 灯光配置数据，偏移 2 为本包字节数 | 两端灯光流处理 |
| 0xE1 | 开始灯光写入，清空接收位置 | 固件 0x77AC |
| 0xE2 | 读取灯光配置 | 固件状态 2，DLL 0x10001A80 |
| 0xE3 | 读取按键计数 | 固件状态 3，DLL 0x10001B70 |
| 0xE6 | 灯光或计数数据流结束 | 两端接收循环 |
| 0xF0 | 键定义数据 | 两端键定义序列化和解析 |
| 0xF1 | 开始键配置写入 | DLL 0x10001860，固件 0x77AC |
| 0xF2 | 读取键配置 | 固件状态 1，DLL 0x100014D0 |
| 0xF6 | 键配置数据流结束 | 固件索引持久化和 DLL 接收循环 |
| 0xF9 | 读取版本 | 固件 0x8740，DLL ReadKeyboardVersion |
| 0xFA 至 0xFF | 外部模块命令转发和参数暂存 | 固件 0x77AC，前台 main 的 UART 处理 |

部分校准和控制命令还位于 `0xD5`、`0xD8`、`0xDB`、`0xDC`、`0xDD`，对应具体软件按钮的语义尚未逐一确认；完整分支保留在自动导出中。

## 键定义记录

载荷 `00 F0 group key type ...` 中，组编号为 1 至 9，物理键编号为 1 至 66。类型 0 表示普通键，类型 1 为连发，类型 2 至 4 对应宏对象的不同模式；具体显示名称和全部时序字段仍需与 GUI 或抓包逐项对应。

| 类型 | 后续字段 |
| --- | --- |
| 0 | 偏移 5 为键码数量，偏移 6 起为内部键码 |
| 1 | 偏移 5 至 6 为大端间隔，偏移 7 为数量，偏移 8 起为键码 |
| 2 至 4 | 固定头 11 字节；偏移 9 至 10 为大端宏数据长度；每个报告承载最多 53 字节宏数据 |

内部键码通过转换表生成 USB 或 UART 报告，不能直接把所有内部值当作 USB HID Usage。内置三列键码和物理扫描位置已导出到 [default_keymap.csv](firmware/tables/default_keymap.csv)。

## 固件记录传输

每行文本去掉冒号后转成二进制，其长度字节和密文保持不变。Windows 发送缓冲区为：

```text
00 00 3A plaintext_record_length DES_ciphertext zero_fill
```

前面的两个 00 分别为 Report ID 和载荷前缀。固件从载荷偏移 2 的长度字段取得明文记录长度，将后续密文长度向上取八字节倍数，再解密并校验 Intel HEX。

类型 4 记录初始化更新暂存状态并暂停相关任务。类型 0 记录按连续地址写入 EEPROM 地址加 4 处，核对读回的数据字节总和。类型 1 EOF 记录检查错误标志和累计校验，写入完成标记并进入后续更新阶段。类型 5 起始地址记录在镜像中存在，当前应用处理器会略过。错误返回载荷包含 `00 3A A0` 或 `00 3A A1`，对应先前记录错误或最终暂存校验失败。

解包脚本输出的标准 Intel HEX 用于分析。完整重建工程的 [package.py](../firmware/package.py) 从编译镜像生成原厂加密封装，基线封装与原文件逐字节一致，可交给配套原厂升级软件。扩展后的 C 扫描镜像也通过完整记录的 ARM 更新处理检查：模拟 EEPROM 暂存数据、读回校验及完成标记均匹配。工程尚未进行实机 USB 传输和片上 LDROM 写回测试，未提供另一个直接访问设备的烧录工具。

Mac `固件升级V1.2.app` 使用同一记录格式：`FileManage` 把行首 `:` 换成 `003a` 再转成字节，形成 `00 3A length ciphertext`，通过 `IOHIDDeviceSetReport` 的 Output 类型、Report ID 0 发送 64 字节。基线全部 3,352 条记录的有效字段与 Windows 编码器一致；这里没有比较记录后未使用的报告尾部字节，也没有执行实际 IOKit 传输。设备字典仅限定 VID `0x0483`，另过滤输出报告长度 64；完整静态检查信息见 [Mac 兼容性记录](../firmware/mac_updater_compatibility.json)。

## 外部模块 UART 帧

`ble_send_frame` 位于 `0x6010`，复制参数到 32 字节暂存区并计算所有参数字节的八位加法和。少于十个参数字节时，帧固定为十字节，补零，校验放在偏移 9；十个或更多参数字节时，校验紧跟数据。

`UART0_IRQHandler` 接收状态字节 0xEA、0xEE、0xE3 和 0xE4，并处理 0xF6 起始的六字节状态记录及 0xF9 触发的版本文本。这里只恢复了应用与外部模块之间的协议，未恢复模块内部 BLE 链路实现。
